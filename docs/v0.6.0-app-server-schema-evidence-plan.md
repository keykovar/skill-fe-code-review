## Status And Purpose

Prepared offline on 2026-09-23. M-02 is a **non-runnable design**, not a frozen runtime window or permission change. No launcher, Seatbelt profile, output directory or generated schema is created by this design step. Stable remains v0.5.0; Gate B is unaccepted, Gate C is blocked and `runtimeReady: false`.

The [frozen actual-role plan](v0.6.0-actual-role-feasibility.md) remains unchanged. M-01 remains `closed-help-stderr-rejection`: its help text is retained as metadata evidence even though its empty-stderr criterion failed. This separately proposed M-02 contract does not retrospectively accept M-01.

The only question for M-02 is whether the pinned CLI can export bounded, inspectable JSON Schema for its app-server protocol. Schema can describe method names and parameter shapes. It cannot establish server initialization, Code Mode routing, command execution, provider compatibility, review quality or full descendant isolation.

## Proposed Invocation

The target argument vector is `app-server`, `generate-json-schema`, `--out`, `<WINDOW>/schema-output`, using the exact installed CLI path selected during future preparation. `<WINDOW>` is an unresolved fresh-directory placeholder. This document is not a shell script.

Use the existing M-01 supervisor/observer as the starting point for offline preparation. Before any runtime decision, pin current binary bytes, argv, profile, environment, directory identities, parser and observer. Binary drift creates a new identity decision, not inherited acceptance. Run at most one target attempt; do not add `--help`, `generate-ts`, a daemon, proxy, listener, host selection, feature override or model option automatically.

The future environment has only the retained fixed PATH, C locale, TERM and NO_COLOR entries plus fresh HOME, CODEX_HOME and TMPDIR paths. Inherit no credentials or user configuration. Stdin is closed; the working directory is fresh and empty. No RPC `initialize`, thread, turn or prompt is sent.

## File And Process Boundaries

| Location or capability | Proposed boundary |
| --- | --- |
| CLI, system libraries, devices and ancestor metadata | Retain the reviewed M-01 access shape after explicit path relocation; grant only the exact CLI execution path. |
| HOME, CODEX_HOME, TMPDIR and workspace | Fresh, empty and unchanged; no new content-read or write grants. In particular, do not grant `$CODEX_HOME/tmp/arg0` writes. |
| `<WINDOW>/schema-output` | A separate fresh empty directory. This is the sole added target data read/write tree. Generated names are not yet known, so file-by-file grants cannot be claimed. |
| Observer receipts and manifests | Separate from schema output; target cannot read or alter these records. The external observer owns capture and inventory. |
| Network, fork and other executables | Denied. No API keys, provider calls, Code Mode host execution or additional execution wildcard. |

`/dev/null` writes remain an inherited exception. The inherited policy starts with allow-default for unlisted operation classes; this is not a claim of complete OS confinement. Exact CLI execution permission can also permit same-path re-exec. Preserve these limits rather than converting process snapshots into proof that no descendant or re-exec occurred.

Before launch, verify canonical output/parent paths, ownership, identities and emptiness. After closure, inventory with no symlink traversal: reject symlinks, hard-linked files, special files, executable files, path escapes and non-JSON leaf files. Preserve every output; do not sanitize, overwrite or delete rejected artifacts. The four isolated directories and all inputs must remain unchanged. An observed mutation outside schema output rejects the attempt, but snapshot comparison does not prove absence of transient writes.

## Proposed Budgets

These are conservative design choices, not documented Codex guarantees. Freeze them before execution; exceeding a limit consumes and stops the attempt without expansion or retry.

| Resource | Limit |
| --- | --- |
| Target attempts / runtime | 1 / 4,000 ms |
| Supervisor envelope | 10,000 ms, retaining bounded TERM/KILL/close handling |
| stdout / stderr | 16 KiB each; retain complete bytes within the cap |
| Schema files / subdirectories / depth | 1,024 / 32 / 8 |
| One schema file / aggregate schema bytes | 8 MiB / 32 MiB |
| Receipt evidence | Retain M-01's 512 KiB evidence allowance and 128 KiB closure reserve; generated schema has its separate budget |

The future observer checks file counts and sizes during execution and before reading content, stops on observed overflow, and performs the bounded final inventory after closure. Sampling is not a filesystem quota: count/aggregate limits are observation and acceptance bounds, not a guarantee that transient disk usage never exceeds them. Do not report such a guarantee.

## Warning And Acceptance Rules

M-02 proposes two distinguishable metadata outcomes. Both require normal exit 0, complete bounded stream capture, the retained ownership/closure receipts, unchanged inputs and isolated directories, and a valid bounded schema inventory. stdout is retained diagnostic text, not a success signal; help output without schema fails.

| stderr bytes | Metadata outcome if every other condition passes |
| --- | --- |
| Empty | `schema-metadata-collected-clean` |
| Exactly one retained M-01 warning, including its final LF | `schema-metadata-collected-with-known-warning` |
| Anything else, including an extra line, repeated warning, altered errno or truncated capture | Rejected |

The only proposed nonempty value is:

```text
WARNING: proceeding, even though we could not create PATH aliases: Operation not permitted (os error 1)
```

Compare raw bytes; do not trim, normalize newlines, use substring matching or suppress stderr. Keep `warningObserved` separate from `schemaEvidenceAccepted`. This exception is proposed only for M-02 metadata collection and adds no helper write permission. Neither accepted metadata outcome passes Gate B or unblocks Gate C. Empty stderr also does not prove aliases were disabled.

Structural schema acceptance requires at least one bounded UTF-8 JSON object with recognizable JSON Schema structure. Reject invalid JSON, duplicate object keys and malformed or escaping local references. Resolve references only within the frozen local output; never fetch remote references or execute generated content. Unresolved external references remain explicit capability gaps. This inspection is not full schema-dialect conformance validation.

After collection, extract method and parameter evidence for `initialize` and `command/exec`, including response/error shapes and relevant command, cwd, timeout and sandbox fields if present. Record exact JSON pointers and supporting file hashes. Do not infer spelling or defaults from current online examples. A missing method/field or unresolved reference produces `Cannot Verify` or `not present`; it does not trigger regeneration with different flags. A collected schema may be valid metadata but insufficient for a later host diagnostic.

## Stop And Result Contract

Unsupported arguments, binary/input drift, overflow, timeout, termination, incomplete closure, unexpected process activity, extra stderr, invalid output or observed boundary mutation prevent acceptance. Stop after the single attempt and preserve all evidence. No automatic schema retry, permission expansion, server startup or model run follows.

The future result must contain the binary/input hashes; exact argv/environment/profile hashes; target and supervisor closure evidence; complete bounded streams; warning classification; schema inventory (relative path, type, size, hash); method/parameter JSON pointers or explicit gaps; metadata acceptance; and unchanged `gateBPassed: false`, `gateCBlocked: true`, `runtimeReady: false`. Direct-process closure and complete descendant observation remain separate fields.
