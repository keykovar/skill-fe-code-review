# v0.6.0 Host Lifecycle Feasibility Decision

## Decision

On 2026-09-23, the bounded offline assessment concludes **No-Go for the selected unprivileged actual-host runtime route under the existing Gate B contract**. None of the assessed mechanisms has evidence for the required combination of registration before execution, complete descendant identity, fork/exec/exit coverage, loss detection and ownership-aware bounded closure.

This is an evidence-limited decision, not a claim that macOS has no possible solution. R-01 startup and R-02 command controls remain `Cannot Verify`; no executable window is prepared. Gate B is unaccepted, Gate C and the selected behavioral pilot remain blocked, and `runtimeReady: false`. This route is stopped pending materially new evidence, rather than queued for another probe.

The [combined isolation contract](v0.6.0-combined-isolation-plan.md), [historical mechanism plan](v0.6.0-process-isolation-mechanism-plan.md) and [protocol analysis](v0.6.0-app-server-protocol-analysis.md) retain their original contents. No acceptance criterion, permission, selected host, client/provider/model or historical outcome is changed by this decision.

## Mechanism Assessment

| Mechanism | Available evidence | Missing requirement or scope conflict | Decision |
| --- | --- | --- | --- |
| `ps` / libproc snapshots and process groups | Process, child and group queries describe visible state at query time | No pre-execution registration or complete event history; short-lived/reparented/regrouped descendants and PID reuse cannot be excluded by before/after queries | Auxiliary snapshots only |
| `kqueue` / `EVFILT_PROC` | Known-PID fork/exec/exit notifications; visible processes can be registered | SDK says child PID is not delivered with `NOTE_FORK`; `NOTE_TRACK`, `NOTE_TRACKERR` and `NOTE_CHILD` are unsupported. Events coalesce. The retained interface does not supply a complete identified descendant ledger with the required loss accounting | Known-child aid only |
| Suspended spawn plus known-PID registration | SDK declares `POSIX_SPAWN_START_SUSPENDED` | A declaration is not runtime validation. Even a successful root registration would not recursively register unknown descendants or establish full shutdown ownership | Does not repair the descendant gap |
| Seatbelt prevention plus native controls | Prior cooperative controls show selected fork/exec/alias/inheritance behavior under their frozen policies | Denying creation cannot simultaneously demonstrate the required local-host startup. Allowing it leaves the opaque descendant gap; cooperative fixture reports are not actual-host evidence. File/process policy also is not a lifecycle event source | Do not convert metadata/native policies into a host profile |
| app-server RPC / EOF / terminate response | Schema and retained docs describe initialization and command-level output/termination | Logical `processId` is not an OS identity. RPC success/EOF does not establish host descendants, registration timing, loss detection or complete reaping. No supported host-wide closure contract is established by the retained artifacts | Insufficient for Gate B |
| Endpoint Security / eslogger / DTrace | SDK/man pages describe richer identity/events or tracing | ES documents entitlement/FDA/privilege requirements and sequence/muting concerns; eslogger requires super-user/FDA, suppresses its group and is not a stable API; execsnoop requires root. These exceed the selected no-extra-permission scope, and observing events alone would still not prove bounded shutdown | Excluded; do not install, enable or launch |

The source IDs `fork-child-id-gap`, `descendant-tracking-unsupported`, `events-coalesce`, `known-pid-filter`, `spawn-definitions-only`, `snapshot-queries`, `es-permissions-muting`, `es-privilege-errors`, `eslogger-permissions-and-suppression` and `dtrace-root` provide the main SDK/man anchors. Process identity and sequence-number excerpts explain what stronger accounting would need; they do not authorize a privileged collector.

Combining snapshots with known-PID events does not supply the missing child identity and registration guarantees. Polling faster, repeating the same successful fixture, changing process groups or accepting an empty final snapshot adds no evidence for events that were never observed. A numeric PID or group signal is not an ownership-safe cleanup mechanism for unknown/reused identities. No such operation is attempted.

## Stopped Work And Reopening Conditions

The next runtime queue is empty for this route: no R-01/R-02 preparation or execution, schema regeneration, repeated source-free probe, Gate C replay, real-key handoff or source-bearing behavioral run follows. Existing outputs remain in place; stopping does not delete evidence or close unrelated user processes. There is no pending permission prompt or scheduled retry.

Reconsider the route only when new, inspectable evidence addresses all applicable prerequisites:

1. A supported interface for the selected current CLI/local host exposes or allows establishing the actual execution graph and stable ownership, without model-selected commands or private source.
2. Registration covers the root and every permitted descendant before relevant execution, including fork/exec, identity changes and reparenting; missing or lost observations are detectable and reject acceptance.
3. A bounded close/cancel/timeout contract proves exit, output/IPC closure and owned-child reaping for every relevant process, including failure paths. A success response or signal attempt alone does not qualify.
4. The mechanism operates within a justified minimal file/IPC/process policy and the selected privilege boundary. Its compatibility with actual local-host startup is evidenced without disabling the host or granting broad execution access.

A new CLI version, metadata field, passing canary or additional user permission alone does not satisfy those technical gaps. Any proposed different execution environment or evaluation route needs its own explicit design and comparable quality/read-only/data-transfer requirements; it does not retroactively accept this route. No such alternative is selected here.
