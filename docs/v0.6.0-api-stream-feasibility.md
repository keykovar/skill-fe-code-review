# v0.6.0 Streaming API Feasibility

## Decision

Current priority, 2026-09-24: **SSE implementation is deferred** at the user's direction. Product work first addresses Origin/Reproduction output correctness; the [documented-label correction](evaluation-results/v0.6.0-origin-occurrence-prototype.md#documented-label-regression) fixes an actual candidate-validator mismatch. The implementation sequence below is retained as a future option, not the current task queue. No streaming receiver or new runtime window has been created.

The earlier offline assessment on 2026-09-24 supports considering a small streaming adapter. Eight authored-data checks confirm that the existing completed-response parser and parameter inspector can be reused. They do not test an SSE decoder, HTTP streaming, provider compatibility or review quality. No new request, credential read, runnable window, dependency or Skill change occurred in that assessment. Stable remains v0.5.0.

The immediate problem is [O-09-02's HTTP 504](v0.6.0-o09-api-review.md#replacement-runtime-result) after 62,906 ms. Its unsupported response type was rejected before body collection. The failing gateway/upstream, buffering policy, exact timeout and model completion remain unknown. Do not treat this as a demonstrated Skill defect or a verified fixed 60-second limit.

Streaming could allow headers and intermediate events to reach the downstream connection before the complete report is ready. This only helps if the selected route supports streaming and forwards those bytes promptly. Gateway buffering, an absolute request deadline or a delayed first upstream event can still produce a timeout. No timeout resolution is claimed.

## Smallest Change

Keep the selected endpoint, model/effort, all eleven instruction/input documents, Prompt, oracle and report contract unchanged. For the O-09 body, change only `stream: false` to `stream: true`; retain `store: false`, disabled tools, disabled truncation, omitted `background` and the requested output cap.

The derived body is 48,304 UTF-8 bytes, SHA-256 `e11790e4a38fafa8c053f6f774ecdf0c15bc4fcdbf7b7ffde5618c4c46263d06`. It was derived in memory and compared structurally with the frozen 48,305-byte body after reversing that one field. No runnable request was saved. This is a proposed transport change, not source-transfer authorization.

## Acceptance Contract

The new adapter must consume a bounded byte stream and retain the raw SSE separately from the extracted final response. Use incremental UTF-8 decoding and explicit SSE frame boundaries so arbitrary byte/chunk splits, multi-line `data`, CRLF boundaries and Chinese text do not corrupt output. Accept comments as keepalives; metadata must never cause reconnection or another request. Define the supported event/field subset in tests before runtime.

Validate the entire event sequence, not only its final object. Track response and item identities and indexes, item types, message parts and observed text deltas. Reject tool/refusal/error/failed/incomplete events, conflicting IDs or content, duplicate completion, malformed JSON/UTF-8 and unsupported events. Reasoning stays separate from report text. Missing required completion or an interrupted stream cannot produce an accepted report.

Only one `response.completed` with one supported final assistant report is eligible for extraction. Observed text deltas and done records must agree with that final report. A text-done event, a partial delta or `[DONE]` alone is not completion. A permitted trailing `[DONE]` is only a terminator, not a second success condition. Wait for normal stream/HTTP closure and reject late conflicting events; never publish partial text as the final review.

Pass the completed envelope through the existing parser, then inspect controls with `stream: true`, verify conversation isolation and reported output limits, and retain missing usage/control echoes as unknown. A transport pass still leaves report acceptance Not Evaluated until the unchanged output validators and complete source-backed adjudication run.

Preserve the one-attempt/no-retry policy, TLS verification, no redirects, no tools, explicit local key input, 262,144-byte request limit, 2,097,152-byte total wire-response limit, 16,384-byte header limit, 16,384 requested output tokens and 300,000-ms absolute HTTP deadline for the proposed review. Events/comments must not reset the deadline. SSE repeats metadata/text, so the unchanged byte cap may reject a large valid stream; report that limit rather than enlarging it automatically. The future small marker probe should retain its smaller existing limits.

For non-2xx or non-SSE replies, retain status and a bounded allowlist of diagnostic headers such as content type, plus a bounded local error-body artifact when available. Do not save credentials, cookies or full headers. Do not print arbitrary error bodies or model content as progress. Mark capture size/truncation explicitly; zero retained bytes are not proof of an empty server response. Local cancellation should close the request and make a best-effort final status record, without claiming remote cancellation or billing cessation.

Show only local phase, elapsed time and received-byte/event counts during waiting. These counters show local activity, not model reasoning progress or provider acceptance.

## Offline Evidence

Eight checks ran against existing pure functions with public dummy objects, without HTTP or a client:

1. A completed envelope preserves the exact authored report text.
2. The existing O-09 assessor rejects an explicit streaming echo as `control-mismatch:stream`.
3. The existing control inspector accepts the same echo when given explicit streaming expectations.
4. A partial text delta cannot be parsed as a completed response.
5. An incomplete response is rejected.
6. A final tool output is rejected.
7. A final refusal is rejected.
8. Missing usage remains unavailable rather than zero.

Request-delta equality was also checked. The original four runtime scripts, requests, results, evaluator and Skill were not edited. These checks establish the reuse boundary only; they are not new streaming test coverage and do not supersede the earlier 182 offline tests or either failed O-09 attempt.

## Deferred Implementation And Validation

Implement a separate bounded SSE decoder/assessment module first, with no filesystem, credentials or network entry point. Its tests should cover successful report/usage preservation, every byte split of a multilingual fixture, multi-line framing, comments/metadata, missing or duplicate terminal events, late errors/tools, item/text mismatch, refusals, truncation, invalid UTF-8/JSON and byte limits. Include cases where the final envelope looks valid but earlier events conflict; the existing JSON parser alone cannot catch those.

Then add a separate injected HTTP streaming sender and fixed-case runner. Use authored request/response objects and fake clocks to test early headers, quiet intervals, malformed content types, HTTP 504 diagnostics, cancellation, delayed callbacks, total-byte limits, absolute timeout despite keepalives and exactly one request. Keep existing frozen scripts/windows intact and avoid a generalized provider/client framework or a new package dependency unless implementation evidence requires one.

After focused offline tests pass, freeze a fresh source-free streaming compatibility request and its launcher for a scoped execution decision. A completed short marker validates only that streaming exchange, not long-response timeout behavior. Only after its assessment should another O-09 execution be proposed with the unchanged input/oracle. Neither provider documentation nor another model/effort selection is a prerequisite for this offline work; actual network execution remains a separate action. O-11/Stage 2 remain Not Run.
