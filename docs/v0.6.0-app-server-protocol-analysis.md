# v0.6.0 App Server Protocol Analysis

## Decision

Prepared offline on 2026-09-23 from the accepted `schema-03` export. **The retained schema is sufficient to describe a minimal initialization exchange, but it does not close the actual-host routing and lifecycle gaps required before R-01.** No startup window is prepared or authorized. Gate B remains unaccepted, Gate C blocked and `runtimeReady: false`. Stable stays v0.5.0.

This step changes maintenance evidence and planning only. It adds no production Skill rule, dependency, installation requirement, runtime launcher or Seatbelt permission. Ordinary Skill users do not need this protocol analysis. The original M-01/M-02 rejection records, accepted replacement metadata and frozen feasibility/schema plans remain unchanged.

## Initialization

| Item | Exact evidence | Consequence for a future diagnostic |
| --- | --- | --- |
| Request envelope | `ClientRequest.json#/oneOf/0` requires `id`, `method`, `params`; method is `initialize` | Use one fixed public request ID and exact method spelling. This is an RPC ID, not a process identity. |
| Parameters | `v1/InitializeParams.json#/required` requires only `clientInfo` | `clientInfo` contains required string `name` and `version`; optional `title` allows string/null. |
| Capabilities | `v1/InitializeParams.json#/definitions/InitializeCapabilities` | `experimentalApi` and `requestAttestation` have schema defaults of false. A future minimal candidate can set both false explicitly, without extension/MCP opt-ins or notification suppression. Defaults remain untested runtime behavior. |
| Completion notification | `ClientNotification.json#/oneOf/0` names `initialized` and requires only `method` | The retained official sequence is `initialize` followed by `initialized`. No separate acknowledgement shape is established for that notification. Do not invent a second response ID. |
| Response candidate | `v1/InitializeResponse.json#/properties` and `/required` | The named type requires `codexHome`, `platformFamily`, `platformOs`, `userAgent`. It exposes neither host PID nor descendant ownership. |
| Generic response | `JSONRPCResponse.json#/properties/result` is `true` | The envelope requires `id` and `result`, but does not enforce an `initialize`-specific result. The named response type is a candidate association, not a machine-linked request/response union. |

A later design should wait for the matching successful initialization response before sending `initialized`, then send no thread, turn, prompt or command. Unexpected messages must be retained within fixed bounds and classified by a frozen policy; dropping them would hide behavior. This is a proposed sequence, not an executable wire transcript or authorization.

The named initialization response could help check the declared isolated CODEX_HOME and expected public platform fields. It cannot prove which host executed, whether configuration/authentication files were accessed or whether a model/provider call occurred. Those require separate OS/request evidence. A future `codexHome` value must be checked against the exact isolated directory rather than accepted as an arbitrary local path.

## Command Contract

`ClientRequest.json#/oneOf/87` names `command/exec` and links `CommandExecParams`. The parameter schema's description and retained official excerpt both describe a standalone command under the server sandbox, without a thread/turn. They do not identify the executor as the selected Code Mode host. R-02 therefore remains separate and blocked.

| Field | Observed schema or annotation | Required design constraint |
| --- | --- | --- |
| `command` | Only required parameter; array of strings. Description says empty arrays are rejected, but there is no `minItems`. | A future evaluator must require a nonempty exact public argv independently. No shell construction or model-selected command. |
| `cwd` | Optional string/null; described default is server cwd | Freeze an explicit canonical public workspace; do not rely on cwd inheritance. |
| `env` | Optional map; values are string/null. Description says overrides are merged into the computed environment. | An empty map does not clear inherited variables. Keep a separate allowlisted outer environment and never supply credentials. |
| `timeoutMs` | Integer/null with `int64` format, no positive minimum | Select a positive bounded duration and retain an independent outer deadline. Do not pair with `disableTimeout`. |
| `outputBytesCap` | Integer/null, minimum zero; described as per-stream bytes | Freeze a positive cap; do not pair with `disableOutputCap`. The JSON cap alone does not bound memory or all descendants. |
| `sandboxPolicy` | Optional; description says omission uses configured policy | Do not inherit an unknown policy. The generated `readOnly` variant has `type` and boolean `networkAccess` (schema default false). |
| `processId` | Optional string, client-supplied and scoped to a connection | It is a logical identifier, never an OS PID, signal target, process group or proof of ownership. |
| `tty`, `streamStdin`, `streamStdoutStderr`, `size` | Descriptions define dependencies on `processId`; PTY implies streaming; size requires PTY | Keep these out of a smallest buffered canary design. A streaming design would need its own decoder, ordering and closure acceptance. |

Do not copy newer-looking examples into this version's request. `permissionProfile` is mentioned in a description but is absent from this export's parameter properties. The retained documentation mentions `access`/`readOnlyAccess`, which are absent from the exported `readOnly` variant. This does not prove that runtime rejection is guaranteed; it means support is not established by this artifact. No regeneration with `--experimental` or fallback to `dangerFullAccess`/`externalSandbox` is authorized. The documented `externalSandbox` variant skips Codex's own enforcement and is not a remedy for the unresolved outer policy.

`v2/CommandExecResponse.json` describes itself as the final buffered `command/exec` result and requires integer `exitCode` plus string `stdout`/`stderr`. That description and the official example support a semantic association. The generic success envelope still lacks a typed method-to-result link. The parameter description says the final response follows process exit and all connection output deltas; this remains an annotation, not observed closure.

The buffered response has no declared truncation flag. Exact expected tiny-canary bytes would be needed for a later bounded comparison; a successful response must not be described as proof that arbitrary output is complete. `command/exec/outputDelta` declares `capReached`, `deltaBase64`, `processId` and `stream`; its description says closing the connection terminates the associated command. This does not document shutdown/reaping of app-server, the Code Mode host or all descendants.

## Errors And Closure

| Evidence | What it establishes | What remains unverified |
| --- | --- | --- |
| `JSONRPCError.json` | Error envelope requires `id` and `error`; error requires integer `code` and string `message`; `data` is unconstrained | Exact method-specific codes, retry semantics, host state and cleanup outcome |
| `command/exec/terminate` at `ClientRequest.json#/oneOf/89` | Request accepts the original connection-scoped logical `processId` | Ownership outside that connection, OS PID identity, descendants and signal/reaping sequence |
| `CommandExecTerminateResponse` | Annotation calls it an empty success response; schema type is object | No required completion/exit fields; success is not verified child reaping. The schema does not even forbid extra object properties. |
| Request/notification catalogs | No exact `shutdown`, `exit`, `app-server/shutdown`, `server/shutdown` or `process/spawn` in the 101 requests plus one client notification | Other names, gated/experimental interfaces, other versions and transport shutdown behavior are outside this bounded absence result |
| Server notifications | `process/outputDelta` and `process/exited` appear, alongside the separate `command/exec/outputDelta` | The experimental process family cannot be substituted for command or host closure; its request is absent from this non-experimental export |

The retained docs explicitly put `process/spawn` outside Codex's sandbox. It is not selected. `thread/environment/disconnected` is likewise not a host-process exit receipt. EOF on app-server stdin or an empty terminate response must not be assumed to reap a local host. No automatic reconnect, retry, alternative method or PID/group signal should follow an unknown or mismatched result.

## R-01 Prerequisite Decision

The smallest possible future actual-role window would start the pinned app-server with its selected local Code Mode host, perform initialization only, and close within a separately frozen budget. It would execute no `command/exec`, thread, turn or model. **It cannot be prepared for execution from the current evidence alone.**

| Prerequisite | Status after this analysis | Required evidence before a startup window |
| --- | --- | --- |
| Initialization field names | Structurally identified | Freeze concrete public request bytes and bounded response parsing after association gaps are addressed |
| Transport and selected settings | Retained docs describe default stdio and local host | Current-binary supported flags/config and exact role selection; do not inherit old `exec` flags or configure a remote host |
| Actual process graph and executor | Cannot Verify | Supported mapping of server/host and any descendants; pre-execution registration, stable identity, fork/exec/exit and loss detection |
| Host startup permissions | Cannot Verify | A separately justified policy. The accepted schema policy denies fork, host execution and network; it is not a server-startup profile. |
| Shutdown and timeout | Cannot Verify | Documented/independently evidenced ownership-aware close and bounded recovery that covers all relevant processes, even across reparenting/group changes |
| Minimal file/IPC requirements | Cannot Verify | Exact justified paths and transports for selected roles, without helper-write expansion, blanket app grants, real config or credentials |

`processId`, RPC success, the initialization `userAgent`, a before/after `ps` snapshot and supervisor direct-child closure do not satisfy the process-graph prerequisite. The prior native cooperative controls stay valid for their declared fixtures; they cannot be promoted to opaque actual-host coverage. The inherited same-path-exec, transient-write and ancestor-race limits remain.

Next make one bounded **offline feasibility decision about an unprivileged, supported host observation and closure mechanism** using retained evidence. Specify its event source, registration timing, stable identities, loss detection and shutdown ownership. If no adequate mechanism can be supported, keep R-01 `Cannot Verify` and stop this runtime route instead of adding speculative probes or widening permissions. No privileged collector, host disabling, alternate model/provider, credential access or source-bearing run is implied. The [combined isolation contract](v0.6.0-combined-isolation-plan.md) remains the gate owner.
