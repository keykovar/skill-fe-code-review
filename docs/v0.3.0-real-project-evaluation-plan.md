# v0.3.0 Real-project Evaluation Plan

Status: Draft

This plan measures `fe-code-review` against real frontend and hybrid-app diffs before any v0.3.0 behavior change is accepted. It complements the deterministic fixtures in `evaluation/fixtures`; it does not replace them or change the public Quick, Deep, or Fix Review contracts.

## Objective

Build a repeatable baseline for review accuracy, severity, scope control, read-only behavior, output stability, and Fix Review closure. Use the baseline to decide whether a Skill change is justified by repeated evidence rather than prompt size, token estimates, or one model run.

## Non-goals

- Do not add a review mode, output section, mandatory JSON schema, or automatic code modification.
- Do not optimize the Skill only to reduce input tokens or improve an implicit-invocation score.
- Do not treat Vitest, a validator, or a synthetic fixture as proof of real-project review quality.
- Do not publish private source, raw traces, credentials, internal paths, or user data as evaluation evidence.
- Do not claim framework, client, runtime, or browser coverage that was not exercised.

## Dataset

Use 6 to 10 distinct real diffs. A case may satisfy more than one dimension, but the final report must show which dimensions were actually covered.

Minimum target matrix:

| Dimension | Minimum | Required characteristics |
| --- | ---: | --- |
| React and TypeScript | 2 diffs | At least one state, effect, ownership, or async-flow change |
| Vue and TypeScript | 2 diffs | At least one composable, store, watcher, or component-boundary change |
| JavaScript | 1 diff | A real contract, compatibility, or maintainability decision without relying on TypeScript diagnostics |
| Hybrid or WebView | 1 diff | A bridge, lifecycle, storage, routing, payment, IM, or environment boundary |
| No clear issue | 1 diff | The correct result permits no actionable finding and a `Keep` design decision |
| Fix chain | 2 chains | An actual previous report, a later fix diff, and per-finding closure evidence |

If a dimension is unavailable, record it as unverified. Do not replace a missing Vue, JavaScript, Hybrid, or client run with a differently scoped case and still claim coverage.

## Case Eligibility

A case is eligible only when:

- The comparison baseline and target revision or working tree are readable.
- The intended submit scope, staged, unstaged, and untracked files can be recorded.
- At least one requirement, bug report, regression test, runtime observation, or owner contract can support adjudication, unless the case intentionally expects no clear issue.
- Generated files and unrelated dirty-worktree changes can be identified and excluded or recorded.
- The review can run read-only without dependency installation, branch changes, formatting, commits, pushes, or production access.
- Any external model transmission of non-public source has explicit authorization for the exact repository, paths, client, and provider.

Reject or pause a case when the baseline is ambiguous, the evaluator cannot distinguish expected behavior from preference, secrets may be exposed, or the selected client cannot inspect the required scope.

## Run Matrix

Complete at least:

- 3 Quick Review runs across different diffs.
- 3 Deep Review runs across different diffs.
- 2 Fix Review runs based on two actual previous reports.
- 1 repeated run for each mode to measure output and decision stability.
- 1 browser-eligible run when a safe, reproducible browser path exists.
- 1 browser-ineligible run that correctly records the affected runtime claim as `Cannot Verify`.

The same diff may be used for a Quick versus Deep comparison, but those outputs are scored separately against their mode budgets. Fix Review must not reuse a fabricated finding list or silently expand into Deep Review.

## Procedure

### 1. Freeze the case

Record the repository identifier, visibility, baseline, target, Git status, intended submit scope, relevant file hashes, framework, language, runtime, and applicable repository instructions. Store a sanitized case ID when the repository name or path is private.

### 2. Prepare evaluator-only expectations

Record known required findings, accepted severity ranges, forbidden findings, expected behavior deltas, and evidence sources. Keep these expectations outside the model-readable workspace and prompt. A model result is invalid if it reads an oracle, previous expected output, or unrelated repository source outside the authorized case scope.

### 3. Run the selected mode

Record the exact prompt, Skill revision, client and version, observable model/provider information, user-level instructions or plugins that may affect the run, allowed validation commands, and browser applicability. Preserve the raw response and trace locally when policy permits.

### 4. Verify every reported finding

Adjudicate each finding from source, call path, test, requirement, or runtime evidence rather than from the model explanation alone:

- `Valid`: the trigger, impact, root cause, and affected contract are supported.
- `False Positive`: the claim is contradicted, invented, preference-only, duplicated as a separate defect, or outside the authorized scope.
- `Cannot Verify`: the evaluator lacks enough evidence to confirm or reject the claim.

Score severity separately. Confirm that the proposed fix is feasible, preserves required behavior, and does not introduce a larger design than the demonstrated problem requires.

### 5. Check missed expectations

Compare the output with evaluator-only required findings. A finding can satisfy an expectation only when it identifies the same trigger and material impact; keyword overlap or a generic test-gap statement is insufficient.

### 6. Check mode and output contracts

Verify localized headings, required scope and evidence sections, conclusion/recommendation consistency, `Design / Simplify`, naming/readability, file placement/module boundaries, test gaps, and static versus runtime evidence boundaries. For Fix Review, verify one status per previous finding, separate New Regression reporting, and no unrelated Deep Review expansion.

### 7. Check read-only evidence

Compare Git status and relevant file hashes before and after the run. Audit the client trace when a supported adapter exists. Any source/configuration write, formatter, dependency installation, branch change, commit, push, oracle read, or unauthorized path access fails the case even when the final answer is semantically correct.

### 8. Record metrics and disposition

Complete the real-project evaluation record. Mark the case `Pass`, `Fail`, or `Cannot Verify`, list the failed gates, and state whether a Skill change, client-specific investigation, fixture change, or no action is justified.

## Metrics

Calculate metrics per mode and in aggregate. Do not combine `Cannot Verify` items into precision or severity denominators; report them separately.

| Metric | Definition | v0.3.0 promotion gate |
| --- | --- | --- |
| Required-finding recall | Detected evaluator-required findings / evaluator-required findings | 100% for mode-required Blocking and Risk findings |
| Finding precision | Valid findings / (`Valid` + `False Positive`) findings | At least 90% per mode |
| False Blocking | Unsupported findings reported as Blocking | 0 |
| Severity accuracy | Valid findings with accepted severity / valid findings with adjudicated severity | At least 90%, with no missed required Blocking severity |
| Suggested-fix quality | Valid findings whose proposed fix addresses the root cause, preserves required behavior, and avoids unjustified redesign / valid findings with a proposed fix | At least 90%, and every Blocking or Risk has a feasible verification method |
| Minimal-design accuracy | Supported `Keep`, `Simplify`, `Extract`, `Redesign`, or `Cannot Verify` decisions / adjudicated design decisions | 100%, with no evidence-free extraction or redesign |
| Recommendation consistency | Runs whose conclusion, gates, and final recommendation agree / completed runs | 100% |
| Output-contract compliance | Runs containing every applicable required section and stable localized heading / completed runs | 100% |
| Read-only violations | Repository or environment mutations caused by review | 0 |
| Scope or oracle violations | Unauthorized path, oracle, expected-output, or outside-workspace reads | 0 |
| Fix closure accuracy | Previous findings assigned the evaluator-supported closure status / previous findings | 100% |
| Fix scope expansion | Fix runs that expand into unrelated Deep Review work | 0 |
| Unqualified runtime claims | Static evidence presented as browser, WebView, device, backend, deployment, or production verification | 0 |

Record elapsed time, output characters, input/output tokens when reliably attributable, tool calls, and retry count as observational metrics. They are not promotion gates until a stable client-specific baseline exists. User-level Memory, plugins, system instructions, and provider retries must not be attributed to the Skill alone.

## Promotion Rules

v0.3.0 is eligible only when:

- Every zero-tolerance gate passes.
- Every required dataset and run-matrix dimension is completed or explicitly excluded from the release claim.
- Aggregate thresholds pass and no per-mode threshold is hidden by another mode's stronger result.
- Two repeated failures support any behavior change; one isolated style preference does not.
- All cases affected by a Skill change are rerun from the frozen baseline.
- Deterministic fixtures, repository tests, both Skill validators, and client runtime acceptance still pass.
- The public evaluation report contains sanitized aggregate evidence and explicit limitations.

If a candidate reduces tokens but lowers recall, precision, severity accuracy, read-only safety, output consistency, or Fix scope control, reject the candidate.

## Evidence Storage

- Use [Real-project Evaluation Record Template](real-project-evaluation-record-template.md) for each run.
- Keep raw private outputs, traces, repository paths, and source hashes in an authorized local evidence location.
- Check in only sanitized records or aggregate results that cannot reconstruct private source or credentials.
- Reference public repositories and commits directly only when disclosure is already permitted.
- Record client and environment limitations as `Cannot Verify`; do not silently omit failed or unavailable runs.

## Exit Deliverables

The evaluation produces:

1. One completed record per run.
2. A coverage matrix for frameworks, languages, modes, clients, and runtime paths.
3. Per-mode and aggregate metrics with raw numerator and denominator values.
4. A failure ledger mapping repeated failures to proposed Skill changes.
5. A sanitized v0.3.0 evaluation result that separates deterministic, model-runtime, browser, and unverified evidence.
