## Alternatives

| Route | Useful evidence it could produce | Cost or unresolved boundary | Recommendation |
| --- | --- | --- | --- |
| Text-only Responses request | Candidate fields, source reasoning, full output shape, severity, IDs, Fix closure and recommendation on the selected fixtures | Requires a new transport contract and provider compatibility check; cannot establish Codex behavior | Recommended for the bounded product pilot |
| Existing local Codex CLI / Code Mode host | Actual selected-client behavior if its full gates pass | Identified descendant observation and bounded closure remain unsupported under the selected scope | Keep stopped; no additional probe without materially new evidence |
| Codex in a separately controlled disposable environment | Potential future client/tool acceptance under a new environment contract | Requires provisioning, suitable binaries, credential/network controls and verified environment shutdown; none is prepared | Defer until client acceptance is the concrete objective |
| Fresh Desktop conversation with manually supplied inputs | Exploratory feedback with little setup | Effective automatic context/tools and transport are not frozen; this current task already knows the answers | Do not count as a controlled replacement or reuse this task as the scored reviewer |
| Cursor or another previously used client | That client's behavior on a new frozen input | Changes client and potentially model routing; historical acceptance does not transfer to current versions or Codex | Not an automatic fallback; requires an explicitly chosen separate scope |

The HTTP option is smaller because the model has no supplied tools and no local action dispatcher. Its response is treated as data. There is no model-controlled shell, MCP, browser, child launcher or file reader to audit. This removes that local agent surface by construction; it does not prove a third-party provider's internal architecture or replace operating-system isolation for a future tool-enabled client.

## Proposed Input Contract

Each request contains one packet only. Use the existing assembly manifest as evaluator-side provenance, validate it against the trusted assembler/raw-input specification, and check the exact regular-file inventory and hashes. A self-consistent edited manifest alone is not sufficient trust. No repository scan, personal configuration discovery or Skill auto-discovery is needed.

1. A short transport wrapper explains that all listed paths are virtual documents embedded in this request, so references to reading files mean inspecting their supplied text. No filesystem or tools are available. This wrapper must not add current case answers or alter review scope.
2. Load the stable core, selected mode and applicable references, then the candidate extension, exactly in `instructionLoadOrder`. Preserve the decoded text and line numbering. Deep retains its required release-risk reference.
3. Supply the existing `PROMPT.md` text and only that packet's raw files in `inputReadOrder`. A structured path/content representation must round-trip to the original UTF-8 bytes; JSON escaping is transport, not a source rewrite. Do not add line-number prefixes to source text.
4. Keep `assembly.json`, source manifests, case/oracle maps, tests, expected reports, previous task conversation and sibling packets outside the request. Fix's authored previous finding and a packet's explicitly supplied observations are legitimate inputs, not evaluator answers.

Proposed role mapping: the transport wrapper and ordered instruction documents form the request's `instructions`; the review Prompt and raw documents form a fresh user input. Freeze and inspect the actual serialized body before any live authorization. This mapping differs from Codex's native instruction loading and must be recorded as part of the API experiment, not assumed equivalent.

The eventual executor needs normal local resource cleanup, explicit TLS verification, an abortable request and strict redirect handling. It does not need the stopped CLI's descendant-tracing infrastructure because that client/host is absent. Do not reuse the old Guard/host acceptance as proof of this new transport. Conversely, do not rebuild its whole process framework for an executor with no child-launch surface.

A client-side deadline limits how long the local operation waits. After timeout, preserve the attempt as incomplete with remote completion/billing unknown, and stop. A token cap is not a guaranteed monetary cap without provider-specific pricing and enforcement. Incompatible or ignored required parameters must stop the window; do not quietly remove controls to make the provider accept a request.

## Offline Contract Implementation

The subsequent [offline script](../scripts/origin-occurrence-api.mjs) has only `prepare` and `parse` operations. It has no HTTP executor, endpoint/config discovery, credential access, child launcher, retries or tool dispatcher. The assembler now shares its existing in-memory specification with a read-only assembly verifier; it does not introduce another packet specification. A manifest must match the trusted current repository specification, including modes, orders, instruction sources and assembler hash, and every regular file must match the expected bytes. Stale assemblies must be rebuilt in a new directory; a self-consistent edited manifest is rejected.

The fixed transport wrapper and a JSON `documents` array form `instructions`. One user message contains JSON with the original `prompt` document followed by the raw `documents` array. Every document has only `path` and `content`. Nested JSON escaping is reversible; there are no line-number prefixes, sibling packets or evaluator manifests. Request bodies contain the proposed model/effort and disabled tool/state controls. They deliberately omit `max_output_tokens` pending the live budget decision, so they remain drafts rather than send-ready requests.

The local candidate bounds are 262,144 request bytes and 2,097,152 response bytes. These are artifact-processing limits only, not adopted live transport, wall-time, token or billing limits. `requests.json` is evaluator-only and records hashes, byte counts, read order, pending live limits and the unchanged false readiness/authorization flags. It must never be included in model input.

```sh
node "scripts/assemble-origin-occurrence-pilot.mjs" --output "<new-assembly-dir>"
node "scripts/origin-occurrence-api.mjs" prepare --assembly "<assembly-dir>" --output "<new-request-dir>"
node "scripts/origin-occurrence-api.mjs" parse --response "<saved-response.json>" --http-status 200 --output "<new-parse-dir>"
```

All output directories must be new and outside the repository; request output must also be outside its input assembly. Parent directories must already exist. Stage 2 selection is available only as an explicit `--stage 2` preparation option after assembling Stage 2. No CLI option executes a request. The parse command's HTTP status is supplied evidence, not an independently observed transport result.

The parser accepts a completed Responses envelope with exactly one completed assistant text message, plus optional opaque reasoning items. It checks all output items and message content, rejects tool calls/unknown items, refusal, missing/unsuccessful HTTP status, response errors, incomplete output, commentary-only messages, malformed UTF-8/JSON, empty text and oversized bodies. Reasoning remains in the retained raw JSON and never enters `report.md`. Multiple assistant messages are unsupported in this initial contract. Unknown top-level provider metadata is not treated as report text.

Missing/null usage becomes `unavailable`; explicit counts must be nonnegative safe integers with consistent totals and bounded known detail counts. Reported model/usage fields are provider claims, not independent identity or billing verification. `response-text-extracted` always retains `reportAcceptance: Not Evaluated`; stable/candidate format checks, field comparison and full-review adjudication remain separate.

For bounded regular response files, parsing preserves the original file and writes a byte-identical `raw-response.json` plus hash and `parsed.json` into a new directory. Rejected bounded content is retained without `report.md`; oversized files are refused before reading, leaving the supplied file untouched. Exclusive creation prevents accidental overwrite, but does not claim OS-enforced write-once storage. No live response has been collected or scored. Exact generated artifacts and verification results are recorded in the linked evidence section.
