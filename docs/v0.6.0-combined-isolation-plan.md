# v0.6.0 Combined Isolation Plan

## Decision

Prepared on 2026-09-16 from retained local evidence. This freezes the remaining test scope, not an executable runtime or a successful isolation result. Stable remains v0.5.0; `runtimeReady: false`. No new CLI, Code Mode host, Guard listener, real credential or provider request runs while preparing this plan.

Use three sequential gates. Implement and run only Gate A next. Gates B and C require their own executable/profile freeze after the preceding gate passes. A failure stops the sequence; a replacement gets a fresh directory and keeps the original failure.

Reuse applies to unchanged components and their recorded scope; a changed component needs focused regression coverage.

## Gate A: Full Worker Handoff

Scope: public dummy data, synthetic PTYs, unchanged reader/decoder/full-worker bytes, fresh role directories and local listeners only. No CLI, Code Mode, local TLS request or model invocation is required. Retain the worker's nine file assertions and denied-port check. Do not grant outbound access to the configured upstream; its counters must remain zero.

The worker starts a 1,500 ms timer before reading fd3 and then fd4. The reader allows 2,000 ms of input time. Launching them together can make the worker expire while valid input is still pending. This is a source-backed timing risk, not a newly reproduced runtime failure.

Freeze this order without increasing either timeout:

1. Create a one-way native pipe with close-on-exec defaults. The parent temporarily retains only its read end after the reader inherits the write end. It never reads, copies or logs the pipe payload.
2. Start the unchanged hidden reader on a fresh PTY. Supply only the 39-byte public canary. Require its accepted result, confirmed exit/output closure and exact terminal restoration before starting the worker. The tiny dummy payload is queued in the pipe; this is not acceptance of arbitrary 4,096-byte real-key buffering.
3. On reader failure, close the pending read end and stop; launch no worker. On success, create the independent config pipe and map the read ends to worker fd3/fd4 with collision-safe descriptor actions. Close the parent's credential copy immediately after successful spawn. Send bounded config once, then close its writer.
4. Start the worker's existing 1,500 ms startup clock only when the worker launches. Wait for ready and the existing role checks, then close its control stdin. Require final state, confirmed exit/output closure and all selected ports closed. Never use a credential/config pipe as a lifecycle control channel.

The runtime launcher must freeze the actual mapping implementation before it runs. Record descriptor direction, ownership, close-on-exec behavior and spawn/close order using nonsecret metadata. Descriptor numbers alone are insufficient because runtimes can reuse fd3/fd4. Use an OS-supported object identity or an equivalent behavioral check; inability to distinguish the original pipe from a reused descriptor is a blocked assertion.

| Role | Credential | Config | Other permitted handles |
| --- | --- | --- | --- |
| Supervisor | Temporary read endpoint, never read; closed after handoff or failure | Write once, close after delivery | PTY test driver, child lifecycle, bounded evidence |
| Hidden reader | Write endpoint only, closed before worker launch | None | PTY stdin, bounded result stdout/stderr |
| Full Guard worker | Read endpoint at fd3 only | Read endpoint at fd4 only | Control stdin, bounded stdout/stderr, permitted loopback listener |
| Later sibling/CLI/host | No endpoint or duplicate of either pipe | None | Only explicitly declared role handles |

Freeze five focused cases, in order:

| ID | New integration assertion | Expected result |
| --- | --- | --- |
| FW-01 | Inject the public canary after 1,750 ms of reader-ready time; then start the full worker | Reader finishes within its 2-second bound; worker becomes ready within its own bound; zero requests; all roles/terminal/ports close |
| FW-02 | Cancel the reader before acceptance | Exact terminal restoration, closed pipe, zero worker launches |
| FW-03 | Deliberately swap credential/config inputs at the worker boundary | Startup rejection, no ready/listener/upstream request, closed descriptors and outputs |
| FW-04 | Deliver valid credential, hold config writer open without EOF | Existing worker `startup-deadline` rejection, no ready/upstream request; supervisor closes held writer |
| FW-05 | Successful handoff, then launch a bounded descriptor witness with the same additional-handle exclusion as a future client | Neither original pipe is inherited; own declared handle works; full worker exits normally |

FW-03/04 deliberately violate one transport condition and are not positive ownership evidence. FW-05 is a descriptor witness, not actual CLI/Code Mode acceptance. The reader's other signals, invalid/oversized input and crashed decoder are covered by retained tests; do not duplicate them here.

Use a 6-second per-case bound and 30-second suite bound including termination/output closure. Retain TERM 250 ms, KILL 750 ms and output-close 100 ms grace within those bounds. The limits are supervisory acceptance bounds, not a kernel termination guarantee. Keep 64 KiB per-stream capture and a 512 KiB aggregate runtime-evidence cap, including 128 KiB reserved for closure. Keep the existing 16 MiB scratch sampling limit if scratch is created; sampling is not a hard quota.

Reader network access stays denied. Reuse its current file scope only as a trusted dummy input helper; do not claim that the earlier network-only reader profile proved file isolation. Full worker file rules must remain role-specific, including the exact root-directory and ancestor exceptions already evidenced. Freeze dynamic ports before spawn. Run a fresh owned-process/UE check before strict launches and confirm exit/output/socket closure afterward.

## Gate B: Process Policy And Actual Runtime

Gate A does not unlock a provider request. First freeze the actual CLI/host execution graph, effective policy and inspection mechanism. Preserve `gpt-6-astra`/`xhigh`, clean context, strict config, exact request equality and response buffering. Do not disable the required host or change client tools merely to get an easier result.

The current CLI profile permits reads of the pinned CLI/host and fresh runtime directories, but does not explicitly constrain process execution. Three startup aliases point to the CLI (`apply_patch`, `applypatch`, `codex-execve-wrapper`); their existence is not evidence they ran or that an execution allowlist distinguishes aliases. Before adopting a process restriction, verify its actual macOS semantics for initial exec, child exec, fork, threads, path aliases and inherited policy. Freeze any indispensable executables individually; no shell, whole application tree or temporary-directory wildcard is an automatic exception.

Begin with harmless public-canary controls against the candidate policy. A Node/native stand-in can establish selected policy operations, but cannot replace actual CLI/host evidence. Then use the pinned actual binaries and the same candidate launch boundary to verify:

- Allowed startup, own scratch and the selected Guard port still work.
- Guard/evaluator/outside canary reads, forbidden writes and alternate live loopback connections are denied from the relevant actual process/descendant.
- Credential/config pipe identities are absent; only the loopback token reaches the CLI.
- Undeclared child execution is denied, and permitted descendants retain the role's restrictions.
- Lifecycle tracking covers descendants that change process group or parent. A polling snapshot alone is not complete spawn/exit coverage.

Record the actual observation mechanism, permissions and its known gaps before launch. If the installed CLI/host cannot exercise a required control through a documented or independently verified interface, mark that assertion `Cannot Verify` and stop. Do not fabricate helper flags, alter the frozen no-tool request, invoke model-selected code to manufacture evidence, or widen OS permissions. The exact subprocess-control case count and executable commands remain blocked pending this mechanism; this plan is not a runnable Gate B manifest.

## Gate C: Representative Combined Replay

Only after Gates A and B pass, freeze two fresh local actual-CLI windows: a fixed safe final, then a late-tool response. Each permits at most one CLI invocation and one local TLS request, with no retry or fallback. These two replays are justified by the changed handoff/process policy; they are not a rerun of the full quality matrix.

Keep the accepted request/response contracts, 15-second request-admission window, 110-second upstream setting, 115-second CLI idle bound, 119-second supervisory stop and 120-second total envelope. Retain bounded scratch/evidence and descriptor/role checks. The normal final must match exactly; the late tool must release zero model bytes. Confirm complete child/output/port closure. Reuse the prior full-duration timeout if its implementation is unchanged; do not promote its clock-tested 119-second fallback to full-duration evidence.

## Evidence And Stop Conditions

Every runtime gate gets a fresh manifest with exact source/executable/policy/argv/environment/cwd hashes, initial inventories, declared scenarios, limits and data categories. Retain bounded case events, fd ownership metadata, terminal comparisons, process lifecycle, socket results, before/after inventories and a final independent audit. Do not persist credential/config payloads, raw environment values, TLS secrets or canary echoes. An echo fails the run; record only a safe reason/count/digest. Fixed public fixture source may contain the canary, but runtime evidence must not.

Stop on binary/input drift, a stale/consumed root, unresolved descriptor identity, unexpected child, missing observation, UE/unconfirmed exit, open output/port, unexpected read/write/network success, token echo, evidence/scratch overflow or a missed deadline. Retain failures without retries. Plan/audit preparation uses no runtime children, so it does not refresh the OS process state; preflight belongs immediately before each future launch.

Remaining separate boundaries include real keyboard-to-foreground signal routing, supervisor-death recovery, best-effort memory clearing, full HTTP parser/network-family coverage, provider compatibility and billing. No local gate alone authorizes credential entry, DNS/provider contact, source-bearing review, Skill installation, cleanup, Git writes or release operations.
