## Product Contract

| Surface | Proposed v0.6.0 behavior | Invariant |
| --- | --- | --- |
| Each Quick/Deep finding and Fix verification/regression item | Add `问题来源 / Origin` and `复现观测 / Reproduction` as two nested fields | No extra top-level section, mode or mandatory JSON output |
| Origin | `New`, `Amplified`, `Retained`, `Unknown`, supported relative to the declared comparison baseline | No invented introducing commit/author; relocation or line age alone is insufficient |
| Fix attribution | Prior issue origin uses the original review baseline; new regressions use the repair baseline | Original severity and IDs stay intact; legacy prose does not acquire fabricated historical IDs |
| Reproduction | `Observed`, `Not Run`, `Cannot Verify`, `Not Applicable`; observed counts are completed failures/trials with provenance | Separate environments, revisions, inputs, schedules and before/after groups; no unsupported percentage or production probability |
| Rare triggers and zero samples | Report a supported material defect and its actual trigger; narrow or withdraw a claim refuted by evidence | Low observed count alone neither suppresses a finding nor proves safety; zero failures alone does not close an issue |
| No finding | Preserve empty severity sections and the applicable Keep decision | No placeholder findings or empty metadata sections |
| Quick/Deep Coverage | Permit existing plain locations or validated matching local file/line links | Same one-line transition, disposition, IDs and merge-key rules; source root supplied independently |
| Fix output | Preserve focused verification, direct regressions, five integer totals and consistent closure | No Coverage ledger or implicit Deep Review expansion |

Keep the complete shared Origin/Reproduction constraints in the main Skill entrypoint. Mode references receive only field placements and their existing mode-specific rules. Do not make important constraints depend on an optional new reference, compress/remove current safeguards, or duplicate these rules for React/Vue/TS/JS. Preserve implicit invocation, read-only operation, language, severity, recommendation matrices, minimum-sufficient-design review, Context7 exclusion and conditional browser evidence.

## Confirmed Blocker

**I-01: legacy Fix compatibility can override an unrelated structural rejection.** The candidate's `validateLegacyFixStructure` checks legacy item shape/status count, then `validateOriginOccurrenceCandidate` accepts `stable.valid || legacyStructureValid`. Consequently, a valid no-ID legacy report with a forbidden Coverage section still returns `structurallyValid=true` even though the raw stable result contains `fix-review-coverage-ledger-forbidden`.

The [read-only diagnostic](../.local-evaluation/v0.6.0-integration-impact-01/diagnose-legacy-boundary.mjs) uses the accepted numbered O-09 report only as an in-memory input control. Its [saved result](../.local-evaluation/v0.6.0-integration-impact-01/legacy-boundary-diagnostic.json) records three controls and sixteen file pins:

| Control | Expected candidate structure | Current candidate structure | Interpretation |
| --- | --- | --- | --- |
| Original numbered Fix | Pass | Pass | Previous O-09 acceptance remains intact |
| Same report, previous ID omitted | Pass under explicit legacy compatibility | Pass | Intended legacy behavior |
| Legacy report plus forbidden Coverage | Fail | **Pass** | Confirmed evaluator false acceptance |

Repair scope: compatibility may reconcile only the exact legacy-ID mismatch that its independent structure checks establish. Keep unrelated stable failures fatal, check status association per item rather than only a document-wide total, and cover missing/duplicate/wrong-level verification sections, forbidden Coverage, malformed/duplicate status and mixed numbered/legacy/new-regression shapes. Do not invent IDs, accept every legacy report, or silently reject behavior the Skill already promises. The diagnostic confirms the Coverage bypass; the other listed shapes are required regression coverage, not newly claimed defects.

The existing candidate validator is pinned by historical windows. Preserve its original source/hash and dependencies for those windows; introduce the repaired evaluator as a new explicit candidate revision. Do not replace old pins or rerun old windows against changed code while presenting them as unchanged historical results. The eventual formal implementation should have one maintained implementation of each rule, not an accumulating chain of implicit fallback adapters.

Repair completed: [legacy-fix-10](../evaluation/prototypes/origin-occurrence/legacy-fix-10.json) selects `validateOriginOccurrenceLegacyFix`. It keeps the original result as `raw`, verifies each item's status and supplied IDs, and checks a validation-only shadow with independently checked legacy items removed. It can reconcile only ID/status mismatches explained by that check; unrelated raw errors remain fatal. No historical IDs are invented. The original diagnostic above is retained as pre-repair evidence.
