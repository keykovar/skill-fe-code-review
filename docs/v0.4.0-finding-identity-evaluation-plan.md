# v0.4.0 Independent Finding and Stable ID Evaluation Plan

Status: Candidate 08 selected for v0.4.0 release at `7 / 7` after tooling-only preserved-trace replay; raw `6 / 7` retained

This plan evaluates one narrow behavior candidate: every distinct actionable issue is emitted as an independent Finding with an ID that remains stable through its Initial Review to Fix Review chain. Candidate instructions and evaluator artifacts were isolated from the published v0.3.0 release until every promotion gate passed; Candidate 08 is the selected v0.4.0 release result.

## Evidence For The Candidate

The candidate is justified by repeated evidence rather than a single output sample:

- The first v0.2.1 Codex Quick run identified all three seeded concepts but discussed the ignored `baseUrl` contract outside an independent `Risk` finding.
- The v0.3.0 post-release Codex Quick run repeated the same failure: the ignored-parameter risk appeared under `Design / Simplify`, so independent-finding recall remained `2 / 3`.
- The current Skill already says actionable design issues belong in a severity section and should only be referenced from `Design / Simplify`. Repeating the failure after that rule shows that a measured clarification is eligible for evaluation.

Historical runs remain unchanged. They are evidence for starting the candidate, not baseline passes and not results that may be carried into the prospective window.

## Objective

Measure whether a minimal identity contract can:

1. Preserve every distinct actionable root cause as one independently scorable Finding.
2. Prevent `Design / Simplify`, naming, test-gap, or evidence sections from substituting for a severity-classified Finding.
3. Let Fix Review close every previous Finding by exact ID without prose-only matching.
4. Preserve severity, recommendation, localized output, read-only behavior, client isolation, and the Quick versus Fix scope boundary.

## Non-goals

- Do not add a review mode, mandatory JSON output, global issue database, content hash, or repository-wide finding registry.
- Do not make IDs stable across unrelated reviews, rewritten reports, rebases, or independently generated review histories.
- Do not encode severity, path, line number, framework, or remediation state into an ID.
- Do not change automatic invocation, Context7 policy, browser-evidence policy, collector behavior, or client adapters during this candidate.
- Do not optimize for token count by weakening accuracy, read-only rules, localized headings, or Fix Review boundaries.
- Do not send private source during this evaluation. Use only checked-in public synthetic fixtures.

## Candidate Contract

The candidate is not accepted until its implementation and runtime window pass every gate below.

### Independent Finding

Emit separate Findings when actionable issues have different root causes, remediation steps, or verification methods. Multiple symptoms may remain in one Finding only when they share the same root cause, repair, and validation path.

Mentioning an actionable issue only under `Design / Simplify`, naming, file placement, test gaps, release risk, or evidence does not satisfy Finding coverage. Those sections may reference a Finding but must not replace it.

### Finding ID

- Initial Quick and Deep Reviews assign `F-001`, `F-002`, and subsequent three-digit sequential IDs.
- Order IDs by severity (`Blocking`, `Risk`, `Improve`), then by the first changed source location supporting the Finding.
- IDs are unique within one review chain and carry no semantic meaning beyond identity.
- A no-clear-issue review emits no placeholder or synthetic ID.
- Fix Review preserves every supplied previous ID exactly once.
- A New Regression receives the next unused `F-NNN` ID after the highest previous ID.
- If the previous report has no IDs, Fix Review retains the current prose-based fallback; it must not invent a false claim that the old report contained stable IDs.

The required stability boundary is one Initial Review to Fix Review chain. A global deterministic fingerprint is intentionally out of scope.

### Cross-section References

When another section discusses an actionable Finding, it references the ID and adds only section-specific context. It does not duplicate or relocate the complete Finding. `Design / Simplify` cannot cite an ID that does not exist in a severity section.

## Metrics

Score semantic concepts, not exact prose.

| Metric | Formula | Required result |
| --- | --- | ---: |
| Independent-finding recall | Expected distinct findings emitted in severity sections / expected distinct findings | `100%` |
| Section-leakage rate | Expected actionable issues present only outside severity sections / expected distinct findings | `0%` |
| Finding-ID coverage | Actionable findings with one valid ID / actionable findings | `100%` |
| Finding-ID uniqueness | Unique valid IDs / all emitted Finding IDs | `100%` |
| Fix closure coverage | Previous IDs with exactly one closure status / previous IDs | `100%` |
| Fix ID preservation | Previous IDs reproduced byte-for-byte / previous IDs | `100%` |
| Repeat identity stability | Oracle concepts retaining the same ID across the unchanged repeat / matched oracle concepts | `100%` |
| Severity accuracy | Expected findings with an allowed severity / expected findings | `100%` |
| False-positive count | Actionable findings unsupported by the oracle or visible evidence | `0` |

Token and elapsed observations are recorded per run but are not Skill-only quality metrics. To prevent instruction growth, the implementation target is a net addition of no more than 90 English words in `SKILL.md` and 120 English words across mode references, with no duplicated invariant or frontmatter expansion. Exceeding that budget is a candidate design failure unless existing text is removed or replaced to keep the net contract within budget.

## Mandatory Gates

Every applicable run must pass independently:

- Complete semantic oracle and allowed severity.
- Finding ID format, uniqueness, ordering, reference, and Fix preservation rules.
- Localized required headings and internally consistent conclusion and recommendation.
- Quick, Deep, and Fix scope budgets, including no Fix-to-Deep expansion.
- One context-collector invocation and zero equivalent Git rereads where the complete-uncommitted collector gate applies.
- Zero write tools, write-capable shell commands, MCP calls, oracle reads, outside-workspace reads, or unapproved endpoint activity.
- Unchanged Git status and frozen relevant file hashes.
- Deterministic fixture behavior, repository tests, both Skill validators, Node syntax, and `git diff --check`.

No aggregate score can compensate for a failed mandatory gate.
